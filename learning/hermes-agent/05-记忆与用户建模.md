# 05-记忆与用户建模

> 理解 Hermes 的 Memory 系统：MEMORY.md、USER.md、Session Search、Honcho 等如何协同工作。

---

## 第一步：概念解释

### Hermes 的记忆系统

Hermes 有三层记忆：

| 层级 | 内容 | 存储 | 管理者 |
|------|------|------|--------|
| **Memory（MEMORY.md）** | Agent 的个人笔记 | 2,200 字符 | Agent 手动 |
| **User Profile（USER.md）** | 用户画像 | 1,375 字符 | Agent 手动 |
| **Session Search** | 所有对话 | SQLite + FTS5 | 自动 |

另外有 **External Memory Providers**（如 Honcho）提供更深层记忆。

---

### 记忆的容量限制

| 文件 | 字符限制 | Token 估算 | 典型条目数 |
|------|----------|------------|------------|
| MEMORY.md | 2,200 | ~800 | 8-15 条 |
| USER.md | 1,375 | ~500 | 5-10 条 |

**为什么有限制？**
- 每次对话都会注入系统提示
- 固定 token 消耗，不会无限增长
- Agent 需要精选最重要的信息

---

## 第二步：类比理解

### 记忆 = 员工的笔记本

Session Search → 完整的日记本（记录所有对话）
Memory → 精选笔记（只记重要信息）
User Profile → 用户档案（记住用户偏好）

**类比：**

```
新员工入职：
- 每天写日记（Session Search，自动）
- 选重要信息记在笔记本首页（Memory，手动）
- 记住老板的偏好（User Profile，手动）

时间久了：
- 日记可以翻看（搜索过去对话）
- 笔记首页是关键信息（系统提示注入）
- 知道老板喜欢简洁回答（User Profile）
```

### Honcho = 深度理解助手

Honcho 提供：
- **知识图谱**：关联信息，理解关系
- **语义搜索**：理解意图，不只是关键词匹配
- **自动提取**：从对话中自动提取事实
- **用户建模**：理解用户的深层意图和风格

## 第三步：代码/实践

### Memory 的系统提示注入

```markdown
══════════════════════════════════════════════
MEMORY (your personal notes) [67% — 1,474/2,200 chars]
══════════════════════════════════════════════
User's project is a Rust web service at ~/code/myapi using Axum + SQLx
§
This machine runs Ubuntu 22.04, has Docker and Podman installed
§
User prefers concise responses, dislikes verbose explanations
```

**格式特点：**
- Header 显示哪个 store（MEMORY/USER PROFILE）
- 使用率百分比和字符数
- 条目用 `§` 分隔
- 多行条目允许

---

### Memory 工具操作

```python
# 添加
memory(
    action="add",
    target="memory",
    content="Project uses Go 1.22, sqlc for DB queries, chi router"
)

# 替换（用 substring 匹配）
memory(
    action="replace",
    target="memory",
    old_text="dark mode",
    content="User prefers light mode in VS Code, dark mode in terminal"
)

# 移除
memory(
    action="remove",
    target="memory",
    old_text="obsolete info"
)
```

**Substring 匹配：**
- 不需要完整条目文本
- 只需唯一子串即可识别
- 多个匹配会报错，要求更具体

---

### 什么该记？什么不该记？

#### ✅ 该记的（Agent 自动记）

| 类型 | 示例 |
|------|------|
| 用户偏好 | "我喜欢 TypeScript" |
| 环境事实 | "服务器运行 Debian 12 + PostgreSQL 16" |
| 纠正 | "不要用 sudo，用户在 docker 组" |
| 约定 | "项目用 tabs，120-char，Google-style docstrings" |
| 已完成工作 | "2026-01-15 迁移数据库从 MySQL 到 PostgreSQL" |
| 显式请求 | "记住 API key 每月轮换" |

#### ❌ 不该记的

| 类型 | 示例 |
|------|------|
| 太模糊 | "用户有个项目" |
| 可重新发现 | "Python 3.12 支持 f-string nesting" |
| 数据块 | 大段代码、日志文件、数据表 |
| 会话临时信息 | 临时文件路径、一次性调试上下文 |
| Context Files 已有内容 | SOUL.md 和 AGENTS.md 内容 |

---

### 好的 Memory 条目示例

```markdown
# 好：信息密集
User runs macOS 14 Sonoma, uses Homebrew, has Docker Desktop and Podman. Shell: zsh with oh-my-zsh. Editor: VS Code with Vim keybindings.

# 好：具体可操作
Project ~/code/api uses Go 1.22, sqlc for DB queries, chi router. Run tests with 'make test'. CI via GitHub Actions.

# 好：教训 + 上下文
The staging server (10.0.1.50) needs SSH port 2222, not 22. Key is at ~/.ssh/staging_ed25519.

# 坏：太模糊
User has a project.

# 坏：太冗长
On January 5th, 2026, the user asked me to look at their project which is located at ~/code/api. I discovered it uses Go version 1.22 and...
```

### Session Search

所有会话存储在 SQLite，支持 FTS5 全文本搜索：

```bash
hermes sessions list  # 浏览过去的会话
```

```python
# Agent 搜索
session_search(query="docker deployment", days=30)
```

**返回：**
- 相关对话片段
- Gemini Flash 摘要（节省 token）

---

### Memory vs Session Search

| 特性 | Memory | Session Search |
|------|--------|----------------|
| 容量 | ~1,300 tokens 固定 | 无限（所有会话） |
| 速度 | 即时（在系统提示） | 需搜索 + LLM 摘要 |
| 用途 | 关键事实，总是在上下文 | "上周讨论了什么？" |
| 管理 | Agent 手动精选 | 自动 |
| Token 消耗 | 固定每次会话 | 按需 |

---

### External Memory Providers

Hermes 内置 8 个外部记忆 Provider：

| Provider | 特点 |
|----------|------|
| Honcho | 知识图谱、语义搜索、用户建模 |
| OpenViking | 跨会话记忆 |
| Mem0 | 自动事实提取 |
| Hindsight | 对话回溯 |
| Holographic | 全息记忆 |
| RetainDB | 持久化 DB |
| ByteRover | 字节级搜索 |
| Supermemory | 超级记忆 |

```bash
hermes memory setup   # 选择并配置 Provider
hermes memory status  # 查看状态
```

---

### 配置

```yaml
# ~/.hermes/config.yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200   # 可调整
  user_char_limit: 1375     # 可调整
```

---

### 安全扫描

Memory 条目会扫描：
- 提示注入模式
- 凭证外泄模式
- SSH 后门尝试
- 不可见 Unicode 字符

威胁内容会被阻止。

## 第四步：知识关联

### 记忆系统的关系图

```
┌─────────────────────┐
│  Session Search     │  ← 所有对话（自动）
│  (SQLite + FTS5)    │     搜索用时才加载
└─────────────────────┘
          ↓ 选择重要信息
┌─────────────────────┐
│  MEMORY.md          │  ← Agent 个人笔记
│  (环境、知识、教训) │     每次会话注入
└─────────────────────┘
          ↓ 记住用户
┌─────────────────────┐
│  USER.md            │  ← 用户画像
│  (偏好、风格、期望) │     每次会话注入
└─────────────────────┘
          ↓ 深层理解
┌─────────────────────┐
│  Honcho/External    │  ← 知识图谱、用户建模
│  Memory Providers   │     按需调用
└─────────────────────┘
```

## 🎯 关键理解

1. **Memory 是精选的**：不是所有东西都记，有容量限制
2. **Session Search 是后盾**：Memory 记不住的可以搜索
3. **系统提示注入**：Memory 在每次会话开始时冻结注入
4. **Agent 手动管理**：Agent 决定记什么，不记什么
5. **Honcho 提供深层理解**：知识图谱、语义搜索、用户建模
