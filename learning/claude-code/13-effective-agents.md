# 构建有效 Agent 的核心原则

> 来源：Anthropic Engineering Blog - Building Effective Agents

---

## 核心观点

> "最成功的实现没有使用复杂框架或专门库，而是用简单、可组合的模式构建。"

---

## Agent 的定义

Anthropic 区分两种系统：

| 类型 | 定义 | 特点 |
|------|------|------|
| **Workflow** | LLM 和工具通过预定义代码路径编排 | 可预测、一致性 |
| **Agent** | LLM 动态决定自己的流程和工具使用 | 灵活、自主 |

```
Workflow = 按剧本演
Agent    = 现场发挥
```

---

## 何时（不）使用 Agent

**核心原则**：找最简单的方案，只有不够时才增加复杂度。

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   单次 LLM 调用 + 检索 + 上下文示例                          │
│       │                                                     │
│       ├── 够用 → 就用这个                                    │
│       │                                                     │
│       └── 不够 → 需要多步骤？                                │
│                 │                                           │
│                 ├── 是 → 任务可预测？                        │
│                 │       │                                   │
│                 │       ├── 是 → Workflow                   │
│                 │       │                                   │
│                 │       └── 否 → Agent                      │
│                 │                                           │
│                 └── 否 → 优化单次调用                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**权衡**：Agent 用延迟和成本换取更好的任务表现，要判断这个权衡是否合理。

## 关于框架的建议

现有框架：
- Claude Agent SDK
- AWS Strands Agents SDK
- Rivet（可视化拖拽）
- Vellum（GUI 工具）

**问题**：
- 多了一层抽象，调试困难
- 容易诱使添加不必要的复杂度

**建议**：
```
先用 LLM API 直接实现 → 很多模式几行代码就行
如果用框架 → 确保你理解底层代码
错误假设是客户错误的常见来源
```

## 基础构建块：增强型 LLM

```
       ┌─────────────────────┐
       │        LLM          │
       │                     │
       │  ┌───┬───┬───┬───┐  │
       │  │检索│工具│记忆│...│  │
       │  └───┴───┴───┴───┘  │
       └─────────────────────┘
```

当前模型可以主动使用这些能力：
- 生成自己的搜索查询
- 选择合适的工具
- 决定保留什么信息

**实现重点**：
1. 针对你的具体场景定制这些能力
2. 提供 LLM 易用的、文档化的接口

**推荐**：通过 [Model Context Protocol (MCP)](https://modelcontextprotocol.io) 实现工具连接。

## Agent 的实战应用场景

### A. 客服支持

为什么适合 Agent：
- 自然对话流程 + 外部信息访问
- 工具集成：客户数据、订单历史、知识库
- 动作可编程：退款、更新工单
- 成功可测量：用户定义的解决标准

**商业验证**：多家公司采用"按解决收费"模式，证明 Agent 效果。

### B. 编码 Agent

为什么适合：
- 代码可通过自动化测试验证
- Agent 可用测试结果作为反馈迭代
- 问题空间结构化、定义清晰
- 输出质量可客观测量

**Anthropic 自己的实践**：
- SWE-bench Verified 基准测试
- 仅凭 PR 描述就能解决真实 GitHub issue
- 自动测试验证功能，但人工审查仍关键

## 工具设计的最佳实践

### 格式选择原则

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   给模型足够的 token "思考"，别写到死胡同                     │
│                                                             │
│   格式贴近模型在网上自然见到的文本                            │
│                                                             │
│   避免"格式开销" - 不需要精确计数几千行代码                   │
│                 不需要字符串转义代码                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### ACI（Agent-Computer Interface）设计

**核心原则**：人类花多少精力设计 HCI，就花多少精力设计 ACI。

**思考方法**：
```
1. 换位思考：如果你是模型，看描述和参数，知道怎么用吗？
   → 好的工具定义包含：示例、边界情况、输入格式、与其他工具的界限

2. 参数命名和描述是否足够直观？
   → 就像给初级开发者写 docstring

3. 测试模型如何使用你的工具
   → 在 Workbench 跑大量示例输入
   → 看模型犯什么错 → 迭代

4. Poka-yoke（防错设计）
   → 改参数让错误更难发生
```

### 实战案例

**SWE-bench Agent 工具优化**：

问题：模型使用相对路径出错（Agent 离开根目录后）

解决：改成绝对路径 → 模型使用无错误

```
花费更多时间优化工具，而不是优化整体 prompt
```

## 三大核心原则

Anthropic 总结的成功 Agent 设计原则：

| 原则 | 解释 |
|------|------|
| **保持简单** | 不要过度设计 |
| **优先透明** | 显式展示 Agent 的规划步骤 |
| **精心设计 ACI** | 工具文档和测试要到位 |

---

## 总结

```
成功 ≠ 最复杂系统
成功 = 适合需求的系统

路径：
1. 简单 prompt → 优化
2. 加评估 → 测量效果
3. 只有简单方案不够时，才加多步骤 Agent
```
