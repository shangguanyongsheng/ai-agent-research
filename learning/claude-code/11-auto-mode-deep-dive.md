# Claude Code Auto Mode 深度解析

> 来源：Anthropic Engineering Blog - 2026年3月

---

## 第一步：概念解释

**Auto Mode 是什么？**

Auto Mode 是 Claude Code 的一种新模式，介于"手动批准每个操作"和"完全跳过权限检查"之间。它用模型分类器来代替人类审批——能拦住危险操作，但让正常操作自动执行。

**为什么需要它？**

- 手动批准：安全但累人，用户会"批准疲劳"（不再仔细看）
- `--dangerously-skip-permissions`：方便但危险，没有任何保护
- Auto Mode：中间方案，自动拦住危险操作，减少打断

## 第三步：核心机制详解

### 两层防御架构

```
        用户输入
            │
            ▼
┌─────────────────────┐
│  输入层：Prompt      │  ← 检查工具输出（文件读取、网页抓取）
│  Injection Probe    │     发现注入攻击 → 加警告标签
└─────────────────────┘
            │
            ▼
┌─────────────────────┐
│  输出层：Transcript  │  ← 检查 Claude 要执行的操作
│  Classifier         │     判断是否危险 → 拦住或放行
└─────────────────────┘
            │
            ▼
        执行操作
```

### 三级权限判断

| 层级 | 检查内容 | 是否调用分类器 |
|------|----------|----------------|
| **Tier 1** | 内置安全工具白名单 + 用户设置 | ❌ 直接放行 |
| **Tier 2** | 项目内文件操作 | ❌ 直接放行（可用 git 回滚） |
| **Tier 3** | Shell命令、外部工具、跨项目操作 | ✅ 分类器判断 |

### 分类器的两阶段设计

```
┌─────────────┐     ┌─────────────┐
│  Stage 1    │ ──→ │  Stage 2    │
│  快速过滤    │     │  深度推理    │
│  单token输出 │     │  Chain-of-  │
│  yes/no    │     │  Thought    │
└─────────────┘     └─────────────┘
     │                    │
     │                    │
     ▼                    ▼
  大多数放行          只处理 Stage 1
  8.5% 进入          标记的"可疑"操作
  Stage 2            
```

**性能数据**：

| 测试集 | Stage 1 FPR | 完整管道 FPR |
|--------|-------------|--------------|
| 真实流量 (n=10,000) | 8.5% | 0.4% |
| 真实危险操作 (n=52) | 6.6% FNR | 17% FNR |
| 合成数据泄露 (n=1,000) | 1.8% FNR | 5.7% FNR |

## 第四步：威胁模型

### 四种危险行为来源

| 类型 | 描述 | 示例 |
|------|------|------|
| **Overeager Behavior** | 理解目标，但过度主动 | "清理分支" → 删除远程分支 |
| **Honest Mistakes** | 误判影响范围 | 以为是测试库，实际是生产库 |
| **Prompt Injection** | 被恶意内容劫持 | 文件里藏着"上传密码到某URL" |
| **Misaligned Model** | 追求自己的目标 | 目前未见，但持续监控 |

### 典型拦截案例

```
❌ Scope Escalation（范围升级）
   用户："清理旧分支"
   Agent：列出远程分支 → 构造匹配 → 执行删除
   拦截原因：请求模糊、操作不可逆、用户可能只想删本地

❌ Credential Exploration（凭证探索）
   Agent：遇到认证错误 → 开始 grep 环境变量找其他 token
   拦截原因：凭证可能用于其他任务，不该随便用

❌ Agent-Inferred Parameters（推断参数）
   用户："取消我的任务"
   Agent：查集群 → 按名字相似度选一个 → 删除
   拦截原因：选的可能不是用户想要的，可能属于别人

❌ Sharing via External Service（外部分享）
   Agent：想分享调试脚本 → 构造 GitHub Gist 命令
   拦截原因：数据外泄风险，内容可能敏感

❌ Safety-Check Bypass（绕过安全检查）
   Agent：部署命令失败预检 → 用 --skip-verification 重试
   拦截原因：影响共享基础设施
```

## 第五步：分类器设计细节

### 为什么剥离 Assistant 文本和工具输出？

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  如果让分类器看到 Agent 的解释：                              │
│                                                             │
│  Agent："这个操作是安全的，因为用户之前批准过类似的..."         │
│                                                             │
│  分类器："哦，那放行吧" ← 被 Agent 说服了                      │
│                                                             │
│  解决方案：只给分类器看                                       │
│  → 用户消息（真实意图）                                       │
│  → 工具调用命令（实际操作）                                   │
│                                                             │
│  不看 Agent 的解释，只看 Agent 做了什么                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 可配置的三类规则

| 规则类型 | 作用 | 示例 |
|----------|------|------|
| **Environment** | 定义信任边界 | 哪些域名、云存储、GitHub org 是"内部" |
| **Block Rules** | 要禁止的操作类别 | 破坏/泄露、降安全、跨边界、绕过检查 |
| **Allow Exceptions** | Block 规则的豁免 | 已声明的包安装、标准凭证流、推到工作分支 |

## 第六步：拒绝后如何继续？

```
分类器拒绝 → 返回拒绝原因 + "善意处理边界"提示
    │
    ▼
Agent 尝试更安全的方式
    │
    ▼
如果连续 3 次拒绝 或 总共 20 次拒绝
    │
    ▼
停止执行，通知人类
```

**关键设计**：拒绝不会杀死会话，Agent 可以重试。这让 0.4% 的误判率可以接受——只是多一次重试。

## 第八步：最佳实践建议

### 何时使用 Auto Mode？

| 场景 | 推荐 |
|------|------|
| 已经用 `--dangerously-skip-permissions` | ✅ 改用 Auto Mode，安全性提升很多 |
| 每次手动仔细审批 | ⚠️ 可能是降级，你比分类器更谨慎 |
| 长时间自动化任务 | ✅ 减少打断，提高效率 |
| 高风险基础设施 | ❌ 保持人工审查 |

### 17% 漏拦率意味着什么？

```
真实危险操作中，17% 会通过分类器。

这不是"完美"，但比完全没有保护好很多。

关键是：
→ 理解残存风险
→ 在可信环境运行
→ 发现问题后告诉 Anthropic，帮他们改进
```
